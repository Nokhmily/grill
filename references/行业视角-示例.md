# 行业视角示例库

以下是 6 个行业的完整场景推演示例。**实际执行时，根据被拷打产品的类型选择最相关的 2-3 个行业进行分析，不需要全部执行。**

---

## 示例产品：专家知识蒸馏工具（skill distillation）

这个产品的通用能力是：输入一段对话/文本，提取其中的知识和方法论，生成可复用的 skill。

---

### 🏥 医学领域 — 住院医师想蒸馏主任医师的临床经验

```
用户背景：3 年经验的内科住院医师，想学习主任的诊断思路
使用场景：把主任查房时的讲解录下来，蒸馏成诊断决策 skill
行业特殊需求：医学知识极度细分，关注微妙的临床经验（手感、直觉、pattern recognition）

使用过程：
第 1 步：上传主任查房录音的文字稿
  → 发现：工具把所有内容混在一起，没有区分"通用原则"和"经验判断"
  → 行业反应：医学里"教科书知识"和"临床经验"是两回事，经验才是最值钱的

第 2 步：想蒸馏"如何从病人面色判断是否缺氧"这种微妙经验
  → 发现：工具只提取了文字表面的意思，丢失了主任说话时的语气和强调
  → 行业反应：主任说"这个要小心"和"这个要非常小心"是完全不同的严重程度

第 3 步：想把蒸馏结果分享给科室同事
  → 发现：生成的 skill 没有标注"适用条件"和"例外情况"
  → 行业反应：医学知识必须有适用范围，一个诊断经验换个科室可能完全不适用

核心缺口：
- 无法区分"原则性知识"和"个人经验判断"
- 无法捕捉语气、强调程度等隐含信息
- 没有"适用条件"和"禁忌症"的标注机制
- 医学术语识别不准确（"心衰"被识别为"心塞"）
```

### 💰 金融领域 — 分析师想蒸馏巴菲特的投资方法论

```
用户背景：券商研究所初级分析师，想学习价值投资的分析框架
使用场景：把巴菲特历年致股东信的分析逻辑蒸馏成选股 skill
行业特殊需求：金融领域重视可量化、可回测、有明确判断标准的方法论

使用过程：
第 1 步：上传巴菲特关于可口可乐投资的分析文本
  → 发现：工具提取了"关注品牌价值"，但没有提取具体的评估指标
  → 行业反应：我要的不是"关注品牌"这种空话，而是"品牌溢价能维持多少年、怎么量化"

第 2 步：想蒸馏"巴菲特的安全边际计算方法"
  → 发现：工具把数学公式和文字说明混在一起，没有结构化
  → 行业反应：投资方法论必须是可执行的 checklist，不是一段描述

第 3 步：想用蒸馏出的 skill 回测过去 10 年的数据
  → 发现：skill 只是一段文字描述，不是可执行的代码/规则
  → 行业反应：金融领域的方法论必须能转化为选股条件和回测策略

核心缺口：
- 无法提取可量化的评估指标和阈值
- 无法将方法论转化为结构化规则或 checklist
- 无法生成可回测的策略代码
- 缺少"历史验证"环节——这个方法论过去的表现如何
```

### ⚖️ 法律领域 — 实习律师想蒸馏合伙人的辩护策略

```
用户背景：法学院毕业 1 年的实习律师，跟着合伙人做刑事辩护
使用场景：把合伙人分析案件的思维过程蒸馏成辩护策略 skill
行业特殊需求：法律推理极其依赖判例引用和法条精确解读，"感觉"不能作为依据

使用过程：
第 1 步：上传合伙人分析一个故意伤害案的讨论记录
  → 发现：工具提取了"要注意证据链完整性"，但没有提取引用的具体法条
  → 行业反应：辩护策略必须有法条支撑，"注意证据链"太空泛了

第 2 步：想蒸馏"如何判断案件是否适合做无罪辩护"
  → 发现：工具把合伙人的判断逻辑简化为几个要点，丢失了条件判断
  → 行业反应：法律判断是 if-else 结构——"如果证据 X 且不存在 Y，则策略 Z"，不能简化为要点

第 3 步：想把辩护策略分享给团队其他律师
  → 发现：生成的 skill 没有标注"本案特殊性"和"可复用部分"
  → 行业反应：每个案件都有特殊性，必须区分"本案专用"和"通用策略"

核心缺口：
- 无法精确提取法条引用和判例编号
- 无法保留条件判断逻辑（if-then 结构）
- 无法区分"本案特殊策略"和"通用辩护方法论"
- 缺少"风险提示"——这个策略在什么情况下可能失败
```

### 🎓 教育领域 — 培训讲师想蒸馏销售冠军的话术

```
用户背景：企业培训师，想把公司 TOP sales 的成交话术提炼成培训材料
使用场景：录制 TOP sales 的客户电话，蒸馏成销售话术 skill
行业特殊需求：教育领域关注"怎么教"而不仅是"是什么"，需要分解步骤、标注重点、设计练习

使用过程：
第 1 步：上传 TOP sales 与客户的完整通话记录
  → 发现：工具提取了话术要点，但没有标注"这句话是在什么客户反应后说的"
  → 行业反应：销售话术的价值在于时机——客户犹豫时说什么、客户异议时说什么

第 2 步：想蒸馏"如何处理客户的价格异议"
  → 发现：工具把所有异议处理混在一起，没有按客户类型分类
  → 行业反应：不同客户类型（价格敏感型、品质导向型）的异议处理方式完全不同

第 3 步：想把蒸馏结果做成培训课件
  → 发现：skill 是一段文字，不是"讲解→示范→练习→反馈"的教学结构
  → 行业反应：培训材料需要教学设计，不是一份话术文档

核心缺口：
- 无法标注话术的触发条件（什么客户反应后用什么话术）
- 无法按客户类型/场景分类
- 无法生成教学结构（讲解→示范→练习→反馈）
- 缺少"常见错误"——新手最容易把话术用错的地方
```

### 🎨 设计领域 — UI 设计师想蒸馏设计总监的审美标准

```
用户背景：2 年经验的 UI 设计师，想学习设计总监对作品的评判标准
使用场景：把设计评审会上总监的点评记录蒸馏成设计审查 skill
行业特殊需求：设计领域大量使用"感觉"类表述（"这个不够高级"、"节奏感不对"），需要转化为可执行标准

使用过程：
第 1 步：上传设计评审会的录音转文字
  → 发现：工具把"这个颜色太跳了"直接提取为"注意颜色"，没有量化
  → 行业反应：设计师需要知道"跳"的边界是什么——色相偏移多少度？饱和度超过多少？

第 2 步：想蒸馏"总监判断界面是否高级的标准"
  → 发现：工具提取了"留白、字体、配色"等关键词，但没有提取具体的判断逻辑
  → 行业反应："高级感"的拆解应该是：留白比例>30%、字体不超过2种、色彩饱和度<60% 等可量化标准

第 3 步：想让蒸馏结果能自动审查新设计稿
  → 发现：skill 是文字描述，不能对接设计工具做自动检查
  → 行业反应：如果能做成 Figma 插件自动标注不符合项就太好了

核心缺口：
- 无法将主观审美表述转化为可量化的设计规范
- 无法关联到具体的设计工具和组件库
- 缺少"示例对比"——符合标准 vs 不符合标准的视觉对比
- 无法生成设计 checklist
```

### 🏗️ 工程领域 — 项目经理想蒸馏资深架构师的技术决策

```
用户背景：3 年经验的后端开发，刚转项目经理，想学习架构师的技术判断
使用场景：把架构师在技术评审会上的决策逻辑蒸馏成技术选型 skill
行业特殊需求：工程领域重视 tradeoff 分析——不是"A 比 B 好"，而是"在 X 条件下选 A，在 Y 条件下选 B"

使用过程：
第 1步：上传架构师关于"为什么选 PostgreSQL 而不是 MongoDB"的讨论
  → 发现：工具提取了"PostgreSQL 更适合结构化数据"，但没有提取决策条件
  → 行业反应：技术选型的核心是条件——数据量多大？查询模式是什么？团队熟悉什么？

第 2 步：想蒸馏"架构师判断系统瓶颈的方法"
  → 发现：工具把架构师的经验简化为几个检查点，没有保留排查顺序
  → 行业反应：排查是有优先级的——先看数据库、再看网络、最后看代码，这个顺序很重要

第 3 步：想把 skill 给新入职的开发参考
  → 发现：skill 里没有标注"这个判断适用的技术栈版本"
  → 行业反应：技术经验有很强的版本依赖性，Node 16 和 Node 20 的最佳实践完全不同

核心缺口：
- 无法提取决策的条件分支（if X then A, if Y then B）
- 无法保留排查的优先级顺序
- 无法标注技术栈版本和适用条件
- 缺少"失败案例"——什么情况下这个决策是错的
```
